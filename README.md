# 다음 진료 (가칭)

뇌졸중 후 집에서 지내며 통원하는 환자의 **보호자**가 집에서 관찰한 것을 표준 형식으로 받아,
다음 진료에서 의료진에게 물어볼 **질문 최대 3개**와,
보호자 없이 어르신 혼자 병원에 갔을 때 치료사가 읽을 **관찰 요약 한 장**을 만드는 도구.

2026 원티드 AI 챔피언십 출품작. 배포 마감 **2026년 9월 20일**.

## 현재 구현·배포 상태 (2026-09-10 병합 기준)

이 저장소에는 세 모듈이 함께 구현되어 있습니다.

- `frontend/` — React 19·Vite PWA. 홈, 온보딩, 주간 기록, 전체 궤적, 진료 준비 카드,
  설정·이어받기·데모와 치료사용 요약 화면을 제공합니다.
- `backend/` — Java 21 Gradle 멀티모듈. 규칙 엔진, Spring Boot API, LLM 질문 정리와
  안전한 템플릿 폴백을 포함합니다.
- `infra/llm/` — Ollama CPU/GPU, 모델 초기화, Tunnel, smoke와 배포 보조 구성을 포함합니다.

보호자는 홈에서 시작해 온보딩 또는 이어받기를 거친 뒤, 주간 기록·전체 궤적·진료 준비 카드·설정을
사용합니다. 치료사용 요약은 보호자 UI와 분리된 읽기 전용 화면입니다. 현재 API·PostgreSQL·Ollama·
cloudflared는 **Ubuntu 노트북 한 대**에서 함께 운영 중입니다(AWS EC2는 구축되지 않았습니다).
실제 운영 경계와 완료 조건은
[`docs/superpowers/specs/2026-09-17-single-host-deployment-design.md`](docs/superpowers/specs/2026-09-17-single-host-deployment-design.md)를
따릅니다.

## 0. 이 문서를 읽는 새 세션에게

이 문서는 제품이 "무엇을 하는가"보다 **"무엇을 하지 않기로 했고 왜 그렇게 정했는가"**에 지면을 더 씁니다.
이 제품은 잘라내는 과정에서 만들어졌고, 잘라낸 것들은 대부분 **매력적으로 보이지만 검증에서 탈락한 것들**입니다.

작업 중 다음과 같은 제안이 떠오르면 **§3을 먼저 읽고 거절하세요.**

- "기능검사 수치를 넣으면 더 객관적이지 않을까"
- "AI가 좋아지고 있는지 판단해주면 좋을 텐데"
- "운동을 추천해주면 유용할 것 같은데"
- "카메라로 자동 측정하면 정확해질 텐데"
- "의료 특화 LLM을 쓰면 더 정확하지 않을까"
- "도움 수준을 5단계로 늘리면 더 정밀하지 않을까"
- "의사소통이나 기억력 항목도 넣으면 좋을 텐데"

전부 한 번씩 검토했고 전부 탈락했습니다. 이유가 §3과 §8에 있습니다.

**결정의 근거는 세 가지입니다.**

1. 현직 물리치료사(팀 구성원) 인터뷰 — 뇌졸중·척수손상 등 중추신경계 환자와 인공관절 치환술 환자 담당
2. 국내 규제 검토 — 디지털의료제품법(2025-01-24 시행), 비의료기관 금지 행위
3. 문헌 — 보호자 대리 응답의 신뢰도, Barthel Index의 Rasch 분석, 능력-수행 격차 연구 (§3 끝에 정리)

## 1. 제품

### 한 문장

> 보호자가 매일 이미 보고 있는 것을 3분 안에 남기게 하고, 그것을 다음 진료에서 쓸 수 있는 질문으로 바꾼다.

### 사용자

**1차 사용자는 보호자입니다. 환자 본인이 아닙니다.**
기존 재활 앱은 거의 전부 환자용(운동 수행)이거나 병원용(운영 관리)입니다.
보호자는 실제 의사결정자인데도 구매자로 정의되지 않아 아무도 그를 위해 설계하지 않았습니다.

**2차 독자는 치료사입니다. 단, 입력을 요구하지 않습니다.**
계정 없음, 로그인 없음, 입력 없음. 읽기 전용 출력만 제공합니다.

**"다음 진료"는 의사 외래와 치료 세션 둘 다입니다.** 보호자와 "병원" 사이의 의사소통이 목적이라 어느 한쪽으로 좁히지 않습니다.
다만 두 산출물의 주기는 다릅니다. 준비 카드는 외래 예약일에 묶이고, 치료사용 요약은 날짜에 묶이지 않습니다(§9).

### 해결하는 문제

보호자는 "우리 부모님이 나아지고 있나"를 알 수 없고,
3분 외래에서 무엇을 물어야 할지 몰라서 아무것도 못 묻고 나옵니다.

치료사는 병원에서 환자가 **할 수 있는 것**(능력)을 봅니다. 집에서 **실제로 하는 것**(수행)은 볼 수 없습니다.
재활 문헌은 이 둘이 자주 어긋난다고 반복해서 보고합니다. 특히 마비 쪽 손은 병원에서는 쓰고 집에서는 안 씁니다.
이 제품은 수행 쪽 기록만 만듭니다. 팀의 치료사도 "집에서 생활하는 건 치료사도 못 보는 부분이라 보여주는 건 좋다"고 확인했습니다.

### 대상

**MVP는 뇌졸중 후 집에서 지내며 통원 재활을 받는 환자의 보호자.**

뇌졸중으로 좁힌 이유:

- 관찰 항목의 뼈대인 MBI가 국내 뇌졸중 재활의 표준 일상생활 평가입니다. "왜 이 항목이냐"의 답이 "치료사가 이미 보는 척도를 보호자 말로 바꾼 것"이 됩니다.
- 실어증·인지 저하가 흔해 **스스로 상태를 설명하기 어려운 환자**가 자연스럽게 정의됩니다.
- 발병 몇 달 뒤 정체기가 오고, 보호자가 "왜 안 늘지"를 가장 궁금해하는 집단입니다.
- 보호자가 실제 의사결정자라는 주장이 가장 잘 성립합니다.

"중추신경 재활" 전체로 두지 않은 이유는 파킨슨 때문입니다. 약효 주기에 따라 하루 안에서도 오르내리는 게 병의 특성이라 §6의 흔들림 규칙이 매주 발화하고 치료사에게도 새 정보가 아닙니다.
발표에서는 "중추신경 재활, 첫 대상은 뇌졸중"으로 말하되 설계와 시드는 뇌졸중에만 맞춥니다.
확장은 관찰 세트를 추가하는 방식으로 합니다(§5). 팀의 치료사가 인공관절 환자도 보므로 정형 세트도 같은 사람에게 검증받을 수 있습니다.

### 검증된 것

물리치료사 인터뷰에서 좋은 평가를 받은 것은 특정 문장이 아니라 **구조**였습니다.
보호자가 기록할 때마다 자기 생각을 남기고, 진료 때 LLM이 그 생각들을 모아
"선생님께 무엇을 어떻게 여쭤보면 좋을지" 정리해 주는 구조입니다
(2026-09-17 제품 소유자 정정, `docs/superpowers/specs/2026-09-17-caregiver-question-synthesis-design.md`).

아래 두 문장은 규칙 엔진이 관찰 기록만으로 만드는 템플릿 질문의 예입니다.
LLM이 꺼져 있거나 보호자 기록이 없을 때 이 형태의 질문이 보입니다.

> "화장실은 혼자 가시게 됐는데 집 안에서 걷는 건 6주째 그대로입니다. 걷기는 왜 안 늘고 있을까요?"

> "일어설 때 얼굴을 찡그리시는 걸 4주 중 3주 봤습니다. 통증일 수 있을까요?"

**두 질문 모두 수치가 하나도 들어가지 않습니다.** 전부 일상 관찰에서 나왔습니다.
첫 번째는 항목 간 어긋남에서, 두 번째는 비언어 신호의 반복 패턴에서 나옵니다.
§7의 교차 감지 로직이 이 두 문장을 만들어내기 위해 존재합니다.

같은 인터뷰에서 확인된 또 하나:

> "환자가 어느 기간에는 좋아지다가 다음 기간에는 안 좋아질 수도 있고,
> 항목별로 어느 부분은 좋아지는데 어느 항목은 안 좋아지는 걸 치료사가 보고 판단할 수 있다."

**흔들림 자체가 치료사에게는 정보입니다.** 이 문장이 §4의 3층 분리를 만들었습니다.

그리고 치료사의 요청 하나:

> "참여 단계를 더 디벨롭시키면 좋겠다."

이 요청이 §5의 3개 축을 만들었습니다. 단계 수를 늘리는 대신 축을 붙인 이유는 §3 끝에 있습니다.

## 2. 절대 규칙

### 하지 않는 것

| 금지                             | 이유                                                      |
| -------------------------------- | --------------------------------------------------------- |
| 좋아졌다·나빠졌다 판정           | 디지털의료기기 정의의 "예후 관찰"에 해당                  |
| 위험도·점수 산출 (낙상 위험 등)  | 위해도 상승 + "발병위험도"는 비의료기관 금지 용어         |
| 운동 처방·생성                   | "자택 방문 물리치료 제공"에 준함. 경쟁 열세 영역이기도 함 |
| 카메라 자동 동작분석             | 국내에 AI 동작분석 의료기기 허가 선례 존재                |
| 진료 녹음                        | 법적 리스크. 대법원 2026-06 판례로 경계가 좁아짐          |
| 치료사에게 입력 요구             | 업무 추가 = 채택 실패                                     |
| 제품명·문구에 "재활" "치료" 사용 | 비의료기관 금지 용어 예시에 명시                          |

### 문구 규칙

**써도 되는 것**

- "화장실 이용이 지켜보기에서 혼자 하심으로 바뀌었습니다"
- "이 변화가 3주째 유지되고 있습니다"
- "1주만 관찰되어 아직 변화라고 보기 어렵습니다"
- "다음 진료 때 이렇게 물어보세요"

**쓰면 안 되는 것**

- "보행 기능이 개선되었습니다"
- "낙상 위험이 감소했습니다"
- "회복이 또래보다 느립니다"
- "병원에 가보셔야 합니다"
- "좋아지시는 것 같은데" — 질문 안이라도 안 됩니다. "도움이 덜 필요해지셨는데"로 씁니다

### 감소를 다루는 방법

**어떤 경우에도 "악화"라고 쓰지 않습니다. "확인 필요"로 씁니다.**
가치 판정을 피하는 것이 규제 방어이자, 보호자에게 잘못된 확신을 주지 않는 방법입니다.

## 3. 잘라낸 것과 이유

**이 절은 되돌리기 방지용입니다. 아래 기능을 다시 넣자는 제안이 나오면 여기를 근거로 거절하세요.**

### 기능검사 전체 (30초 의자 앉았다 일어서기, TUG) — 제거됨

한때 이것이 제품의 핵심이었습니다. 물리치료사 인터뷰에서 탈락했습니다.

> "측정 자체가 치료사마다도 너무 다르고 주관적인 부분이 커서, 횟수가 늘든 줄든 치료사마다 견해가 다르다.
> 그리고 **측정 과정을 치료사가 본 게 아니라서 신뢰를 못 한다.** 그냥 참고 정도."

정확도 문제가 아니라 **관찰되지 않은 측정**이라는 구조 문제라, 프로토콜을 아무리 조여도 해결되지 않습니다.
문헌도 같은 방향입니다. 자가측정과 치료사 측정을 비교하면 개인 MDC가 6.4회까지 벌어집니다.

추가로, 치료사는 **보호자에게 집 상황을 잘 묻지 않는다**고 답했습니다.
"묻는 시간을 줄여준다"는 가치 제안 자체가 성립하지 않습니다.

부수 효과로 아래 반론도 함께 사라졌습니다.

> "병원에 회복하라고 보냈는데 집에서도 내가 측정을 하고 지켜봐야 한다고?"

**관찰은 노동 추가가 아닙니다. 보호자는 이미 매일 보고 있습니다.**
따라서 모든 카피는 "측정하세요"가 아니라 **"보신 걸 남겨두세요"**로 씁니다.

### MDC 상수 테이블 — 제거됨

기능검사와 함께 제거. 침묵 게이트의 개념은 남았고, 판정 기준만 §6의 관찰 기반 규칙으로 대체되었습니다.

### 보행속도 — 애초에 미포함

스마트폰 측정의 일치 구간(±12cm/s)이 검출해야 할 변화(9.4cm/s)보다 큽니다.

### 도움 수준 5단계 이상 — 미포함

뇌졸중 환자에게 Barthel Index를 Rasch 분석하면 대부분 항목에서 **중간 범주가 "어떤 환자도 가장 고르지 않는 답"**으로 나와 결국 독립/의존 2단계로 접힙니다.
보행 설문 ABILOCO는 환자가 "어렵다"는 중간을 구분하지 못해서 아예 2단계로 만들어졌습니다.
K-MBI가 5단계인 건 훈련받은 치료사가 직접 보고 매기기 때문입니다.
보호자에게는 4단계도 많은 편입니다. 깊이는 단계가 아니라 **축**으로 만듭니다(§5).

### 의사소통·기억·감정 항목 — 미포함

Stroke Impact Scale 대리 응답 연구에서 환자-보호자 일치도는 신체 영역 0.61~0.83, 감정 영역 0.17이었습니다. 기억, 의사소통, 사회참여도 낮습니다.
**보호자는 눈에 보이는 신체 동작에서만 믿을 만합니다.** 관찰 항목은 전부 신체 동작으로 제한합니다.
"약 챙겨 드시기"는 눈에 보이므로 후보로 남습니다(§11).

### 안전·낙상 축 — 미포함

"휘청거림" "넘어질 뻔" 같은 축은 치료사가 원하겠지만 §2의 위험도 산출 금지에 걸립니다. 자유 기록에서 자연스럽게 나오게 둡니다.

### "보호자가 대신 해버리는지" 축 — 미포함

치료사가 궁금해하는 것이지만, §9에서 홈프로그램 미수행 사유를 뺀 것과 같은 이유로 보호자를 탓하는 것처럼 보입니다. 자유 기록에 맡깁니다.

### 범용 관찰 세트 — MVP 미포함

정형 재활(고관절 골절, 무릎 치환)에서 보호자가 보는 건 통증, 걷는 거리, 관절 움직임이라 지금 항목과 안 맞습니다.
세트를 분리해두고 MVP는 뇌졸중 세트 하나만 출시합니다.

### 참여 단계 확장의 근거 (문헌)

- **대리 응답의 편향은 일관됩니다.** 보호자는 환자를 실제보다 더 나쁘게 매기는 경향이 있습니다. 절대값은 못 믿어도, **같은 사람이 같은 집에서 매주 보면 편향이 상쇄되고 변화만 남습니다.** 관찰 환경을 집으로 고정한 이유이고, 작성자가 바뀌면 궤적이 끊긴다는 뜻이기도 합니다(§4).
- **치료사 척도에 이미 "도구" 축이 있습니다.** FIM은 7단계 중 6단계를 "보조 도구를 쓰거나 시간이 더 걸리지만 혼자 함"으로 따로 둡니다. 보조 도구 축은 치료사에게 익숙한 개념입니다.
- **마비 쪽 손은 집에서만 보이는 것 중 문헌이 가장 두껍습니다.** 병원에서는 쓰고 집에서는 안 쓰는 격차가 중등도 이상 마비에서 가장 크고, 가속도계 연구에서는 능력이 늘어도 사용량은 안 따라왔습니다. 보호자 관찰 척도(Motor Activity Log 보호자판)는 신뢰도가 낮았지만 환자 응답과 상관은 0.70~0.73이었습니다. **점수가 아니라 "쓰는지 안 쓰는지" 수준이면 쓸 수 있습니다.**
- **실어증 환자의 통증은 관찰 항목으로 잡습니다.** 실어증 환자 통증 유병률 44~88%, 편마비 어깨 통증 22~47%. 검증된 도구가 없어 치매용 관찰 척도(PAINAD)의 항목을 빌립니다. 표정, 소리, **팔을 감싸거나 특정 동작을 피함.**
- **그림 척도는 비전문가도 치료사 수준으로 매깁니다.** 그림과 분기형 질문으로 만든 Longshi 척도의 비전문가 평가자 간 신뢰도가 0.88~0.96이었습니다. 4단계 선택지를 그림으로 줍니다.
- **뇌졸중 피로는 시간대 패턴이 있습니다.** 활동량이 오전에 높고 오후로 갈수록 떨어집니다. 자유 기록의 시간대 태그(§5)가 여기서 나왔습니다.

## 4. 3층 분리 — 가장 중요한 아키텍처 원칙

**v1의 오류를 고친 부분입니다. 여기를 잘못 구현하면 제품이 정보를 잃습니다.**

세 층은 서로 다른 규칙을 따릅니다. 절대 섞지 마세요.

### 층 1 — 기록 (저장소)

**보호자가 입력한 것은 하나도 버리지 않습니다.** 예외 없습니다.

되돌아간 변화, 1주만 관찰된 것, 항목별로 엇갈린 것, 자유 기록 원문 전부.
주차별 **전체 스냅샷**으로 저장합니다. 델타만 저장하면 나중에 재계산이 불가능합니다.

**값마다 출처를 붙입니다.** 보호자가 직접 고른 값(`confirmed`)과 "달라진 것 없음"을 눌러 지난주 값이 복사된 것(`carried`)을 구분합니다.
걷기의 `1 1 1 1 1 1`이 실제 관찰 1회와 "없음" 탭 5회일 수 있습니다. 치료사가 이 둘을 같은 숫자로 보면 안 됩니다.

**스냅샷마다 작성자를 붙입니다.** 대리 응답의 편향은 사람마다 다릅니다. 작성자가 바뀌면 그 지점을 Layer 3에 표시합니다.

### 층 2 — 보호자 화면 (침묵 게이트 적용)

**침묵 게이트는 여기서만 작동합니다.**
매주의 오르내림을 그대로 보여주면 "좋아졌어요 → 나빠졌어요"가 반복되는 롤러코스터가 되고,
보호자는 혼란스러워하다 이탈합니다.

단, **전체 궤적을 볼 수 있는 별도 탭은 제공합니다.** 기본 화면은 조용하게 두되, 보고 싶은 사람은 볼 수 있게.

### Layer 3 — 치료사용 요약 (전체 궤적 노출)

**흔들림을 그대로 보여줍니다.** 이게 치료사가 판단 재료로 쓰는 정보입니다.

이전값과 현재값만 주면 중간 과정이 사라집니다.
`2 → 3`으로 요약된 항목이 실제로는 `2 2 3 3 2 3`이었다면, 그 흔들림이 치료사가 보고 싶은 것입니다.

`carried` 값은 옅게, 작성자 변경은 세로선으로 표시합니다. 판정은 붙이지 않습니다.

> **핵심 구분: 보호자에게 안 보여주는 것과 기록에서 지우는 것은 다릅니다.**
> v1은 이 둘을 섞어서 `reverted`를 아예 침묵 처리했습니다. 그건 정보 손실입니다.

## 5. 데이터 모델

### 관찰 세트

항목·축·표시 문구를 **관찰 세트** 단위로 묶어 설정으로 둡니다. MVP는 `stroke` 세트 하나.
온보딩의 진단명 선택이 세트를 고르는 스위치입니다. "모름"은 `stroke`로 갑니다(MVP에 세트가 하나뿐이므로).

**표준 코드와 표시 문구를 반드시 분리해서 저장하세요.** 항목 조정 요청이 올 예정입니다.

**MVP에서는 이 세트가 엔진 코드 안의 컴파일된 상수입니다** (`ObservationSet.STROKE`). DB나 설정 파일로 옮기지 않은 건 놓친 게 아니라 의도적으로 미룬 후속 작업입니다 — 세트가 하나뿐인 지금은 코드가 곧 설정이고, 항목 조정 요청이 실제로 오면 그때 외부화합니다.

### 항목 (stroke 세트, 8개)

MBI 구조를 따르되, 화면에는 보호자가 쓰는 말로 표시합니다.

| code         | 표시 문구               | group    | 적용 축                  |
| ------------ | ----------------------- | -------- | ------------------------ |
| `transfer`   | 침대·의자에서 옮겨 앉기 | mobility | level, aid, consistency  |
| `ambulation` | 집 안에서 걷기          | mobility | level, aid, consistency  |
| `stairs`     | 문턱·계단               | mobility | level, aid, consistency  |
| `toilet`     | 화장실 이용             | selfcare | level, consistency       |
| `dressing`   | 옷 입기                 | selfcare | level, consistency, hand |
| `grooming`   | 세수·양치               | selfcare | level, consistency, hand |
| `bathing`    | 목욕                    | selfcare | level, consistency       |
| `feeding`    | 식사                    | selfcare | level, consistency, hand |

### 축 (4개, 전부 순서 있음)

**축이 4개라고 매주 4개를 다 묻는 게 아닙니다.** 화면 2는 달라진 항목만 묻고, 그 항목의 축만 묻습니다(§9).

**`level` — 도움 수준.** 모든 항목. 그림 선택지.

| 값  | 표시 문구   |
| --- | ----------- |
| 3   | 혼자 하심   |
| 2   | 지켜보면 됨 |
| 1   | 손 잡아드림 |
| 0   | 대부분 도움 |

**`aid` — 보조 도구.** mobility 항목만. "무엇을 잡고 하는지."

| 값  | 표시 문구        |
| --- | ---------------- |
| 4   | 아무것도 안 잡음 |
| 3   | 가구·난간 잡음   |
| 2   | 지팡이           |
| 1   | 워커             |
| 0   | 휠체어           |

**`consistency` — 한 주 일관성.** 모든 항목. "이번 주에 그 정도로 하신 게 얼마나 자주였는지."

| 값  | 표시 문구    |
| --- | ------------ |
| 2   | 매번         |
| 1   | 대체로       |
| 0   | 좋은 날만    |

**`hand` — 마비 쪽 손 사용.** 손을 쓰는 selfcare 항목(식사·세수·옷 입기)만. 온보딩에서 마비 쪽을 받은 경우만 활성화.

| 값  | 표시 문구             |
| --- | --------------------- |
| 2   | 주로 씀    |
| 1   | 거들기만   |
| 0   | 안 씀      |

화면에서는 0단계 아래에 "성한 손으로만 하심"이라는 설명을 덧붙입니다. 저장·문장 생성에 쓰는 문구는 표의 짧은 쪽입니다.

`level`이 같아도 `aid`가 워커에서 지팡이로 바뀌거나 `hand`가 "거들기만"에서 "안 씀"으로 바뀌면 치료사에겐 큰 정보입니다. §7 (f)(g)(h)가 이걸 씁니다.

### 비언어 신호

온보딩의 "말씀으로 불편한 곳을 알려주시나요?"에 **가끔/거의 어려움**을 고른 경우에만 활성화.
활성화되면 **변화가 없는 주에도 매주 묻습니다.** 빈도가 정보이기 때문입니다.

- `pain_signal`: 어떤 동작에서 어떤 신호를 봤는지. 동작(다중 선택 + 없음) × 신호
  - `grimace` 찡그림
  - `vocal` 소리를 냄
  - `guarding` 팔을 감싸거나 특정 동작을 피함 — 편마비 어깨 통증용. v3에서 추가
- `sleep`: 야간 수면 (3단계)
  - `0` 자주 깨심 / `1` 가끔 깨심 / `2` 잘 주무심 — 다른 모든 축과 같이 값이 클수록 좋은 쪽입니다
  - 치료사용 관찰 요약(화면 5)에도 그대로 나갑니다

### 자유 기록

- **항목별 한 줄** — 각 참여 항목 아래. 선택 사항
- **기타 자유 기입** — 매주 마지막. 선택 사항
- **시간대 태그** — 오전 / 오후 / 저녁 / 상관없음. 선택 사항. 뇌졸중 피로의 시간대 패턴을 LLM 없이 규칙으로 잡기 위해
- **자유 기록 칸을 넓게 두고, 폰 키보드의 받아쓰기를 쓰도록 첫 사용 때 안내합니다.** 타이핑은 부담이지만, 음성 인식을 우리가 만들지는 않습니다. 이미 손에 익은 키보드를 쓰는 편이 대상 사용자에게 쉽고, iOS·안드로이드 편차도 없습니다
- 원문을 **반드시 그대로 보존**하세요. 치료사용 요약에 원문이 그대로 나갑니다
- 시간대 태그 목록은 **기록된 주마다 항목 하나**입니다. 그 주에 보호자가 태그를 고르지 않았으면 태그 없이(비워서) 올라가고, 기록 자체가 없는 주만 목록에서 빠집니다. 이 목록의 길이가 §7 (e)가 만드는 문장의 분모 — "4주 중 3주"의 4 — 가 됩니다

### 주차 스냅샷

```
{
  week: 1..n,
  author: 작성자 식별자,
  items: {
    [code]: {
      level:       { value, source: 'confirmed' | 'carried' },
      aid:         { value, source } | null,
      consistency: { value, source } | null,
      hand:        { value, source } | null,
      note: string | null
    }
  },
  pain_signal: { [동작]: ['grimace' | 'vocal' | 'guarding'] } | null,
  sleep: 0 | 1 | 2 | null,
  free_note: { text, time_tag } | null
}
```

한 주에 스냅샷이 아예 없으면 **결측 주**입니다. `carried`와 다릅니다.

## 6. 침묵 게이트 — 결정론적 규칙 엔진

**제품의 심장입니다. LLM으로 구현하지 마세요.** 순수 함수 + 테스트로 구현합니다.
같은 입력에 항상 같은 출력이 나와야 합니다. LLM이 판정하면 데모 중에 다른 말이 나옵니다.

**축마다 따로 돌립니다.** `level`, `aid`, `consistency`, `hand` 전부 순서 있는 값이라 같은 함수를 씁니다.
한 항목의 궤적은 축 수만큼의 판정을 냅니다.

### 반환값

```
입력: 한 항목·한 축의 주차별 값 배열 [{ week, value, source } | null(결측)]
출력: {
  status: 'no_change' | 'observed_once' | 'sustained' | 'fluctuating',
  direction: 'up' | 'down' | null,
  since: 주차 | null,       // 현재 방향의 첫 변화가 관찰된 주
  duration: since부터 현재까지 기록된 주 수,
  reversals: 방향 전환 횟수, // §7 (d)가 씀
  trajectory: 입력 배열 그대로   // 항상 전체를 함께 반환
}
```

**`trajectory`는 판정과 무관하게 항상 채워서 반환합니다.** Layer 3이 이걸 씁니다.

### 용어

- **변화**: 기록된 직전 주와 값이 다른 주. 결측 주는 건너뛰고 비교합니다.
- **방향 전환**: 직전 변화와 반대 방향인 변화.
- **현재 값 유지 주 수**: 마지막 변화 이후 현재 값이 이어진 기록된 주 수 (변화 주 포함). 판정 규칙이 씁니다.
- **`since`**: 같은 방향 변화가 연속된 구간의 첫 주. 방향 전환이 없으면 변화가 여러 번이어도 첫 변화 주.
- **`duration`**: `since`부터 현재까지 기록된 주 수. 현재 값 유지 주 수와 다를 수 있습니다. `no_change`일 때는 기록된 전체 주 수.

**`duration`과 문장에 쓰는 "N주째"는 항상 기록된 주 수를 셉니다. 달력상 지난 주 수가 아닙니다.**
결측 주까지 지난 것으로 세서 "N주째"라고 말하면, 보호자가 기록하지 않은 주에도 그 상태였다고 주장하는 셈이 됩니다.
관찰하지 않은 것을 관찰한 것처럼 말하는 것이라 §2가 금지하는 것과 같은 이유로 하지 않습니다.

### 판정 규칙 (위에서부터 순서대로 적용)

```
1. 변화가 하나도 없음                          → no_change
2. 현재 값 유지 주 수가 4 이상                  → sustained   (그 전에 흔들렸어도 회복으로 봄)
3. 궤적에 방향 전환이 하나라도 있음              → fluctuating (v1의 'reverted'를 대체)
4. 현재 값 유지 주 수가 1                       → observed_once
5. 현재 값 유지 주 수가 2 또는 3                → sustained
```

`direction`은 마지막 변화의 방향.
`1 1 2 2 3 3`은 방향 전환 없이 두 번 올랐으므로 sustained up, since 3주, duration 4 (현재 값 유지 주 수는 2).

### 예시 (테스트 케이스로 그대로 옮기세요)

| 궤적                  | status        | direction | since | duration | reversals |
| --------------------- | ------------- | --------- | ----- | -------- | --------- |
| `2 2 2 2 2 2`         | no_change     | null      | null  | 6        | 0         |
| `2 2 3`               | observed_once | up        | 3     | 1        | 0         |
| `2 3 3`               | sustained     | up        | 2     | 2        | 0         |
| `1 1 1 2 2 2`         | sustained     | up        | 4     | 3        | 0         |
| `3 3 3 2 2 2`         | sustained     | down      | 4     | 3        | 0         |
| `1 1 2 2 3 3`         | sustained     | up        | 3     | 4        | 0         |
| `2 2 3 3 2`           | fluctuating   | down      | 5     | 1        | 1         |
| `2 2 3 3 2 3`         | fluctuating   | up        | 6     | 1        | 2         |
| `2 2 3 3 2 3 3 3 3`   | sustained     | up        | 6     | 4        | 2         |
| `2 2 _ 3 3` (3주 결측) | sustained     | up        | 4     | 2        | 0         |

### 결측 주와 복사된 값

- **결측 주**(스냅샷 없음)는 비교에서 건너뜁니다. sustained를 끊지 않습니다. 단 2주 이상 연속 결측이면 Layer 3에 "기록 공백"으로 표시합니다.
- **`carried` 값**은 정상 값으로 취급해 판정합니다. "달라진 것 없음"도 관찰이기 때문입니다. 단 Layer 3에서 옅게 표시하고, 기록 밀도에서 `confirmed` 주 수를 따로 셉니다.

### 층별 처리

| status          | 층 2 (보호자 기본 화면)                                       | 층 2 (궤적 탭) | Layer 3 (치료사용)        |
| --------------- | ------------------------------------------------------------- | -------------- | ------------------------- |
| `no_change`     | 표시 안 함                                                    | 표시           | 한 줄로 접어서 표시       |
| `observed_once` | "한 번 달라진 것으로 관찰됐습니다"                            | 표시           | **전체 궤적 표시**        |
| `sustained`     | "3주째 유지되고 있습니다"                                     | 표시           | **전체 궤적 표시**        |
| `fluctuating`   | **표시 안 함.** 단 sustained에서 넘어온 첫 주만 아래 문구 1회 | 표시           | **전체 궤적 표시 — 중요** |

**이 표가 잠그는 것은 층 2 기본 화면의 변화 목록뿐입니다. 질문 목록은 다른 규칙을 따릅니다.**
§7 (d) 흔들림 질문처럼 방향이 없고 의문형인 질문은 §4가 막으려는 "좋아졌어요 → 나빠졌어요" 롤러코스터가 아니므로,
그 항목의 `level`이 `fluctuating`이어도 보호자 기본 화면에 나올 수 있습니다.

**sustained → fluctuating 전환 주의 문구.** 보호자가 지난주에 "3주째 유지"를 봤는데 이번 주에 그 문장이 말없이 사라지면 그것도 작은 롤러코스터입니다. 전환된 주에 한 번만 이렇게 보여주고 다음 주부터 조용히 둡니다.

> "3주 유지되던 변화가 이번 주에는 다르게 관찰됐습니다. 아직 어느 쪽인지 알기 어렵습니다."

`fluctuating`이 층 2에서만 조용하고 Layer 3에서는 그대로 나가는 것,
이것이 v1에서 틀렸던 부분입니다.

### 비언어 신호 판정

```
최근 기록된 4주 중 1주 관찰      → 기록만
최근 기록된 4주 중 2주 이상       → 패턴으로 발화 (동작·신호 종류별로 따로 셈)
```

## 7. 교차 감지

§1의 검증된 질문 두 개를 만들어내는 로직입니다.
**교차 감지 자체는 규칙 엔진이고, 결과를 문장으로 바꾸는 것만 LLM이 합니다.**

아래 "상승/하락/정체"는 모두 `level` 축의 §6 판정입니다. (f)(g)(h)만 다른 축을 씁니다.

### (a) 상승 대 정체

하나는 `sustained` 상승인데 다른 하나가 `no_change`이면 감지. **그룹 무관.**
(v2는 같은 그룹 안으로 제한했는데, 검증된 질문 1의 화장실(selfcare)과 걷기(mobility)가 그룹이 달라서 규칙이 예시를 못 만들었습니다.)

> 검증된 예시: `toilet` 상승 + `ambulation` 정체
> → "화장실은 혼자 가시게 됐는데 집 안에서 걷는 건 6주째 그대로입니다. 걷기는 왜 안 늘고 있을까요?"

### (b) 상승 대 하락

같은 6주 안에 `sustained` 상승 항목과 `sustained` 하락 항목이 동시에 존재하면 감지. 그룹 무관.

> 예시: `dressing` 하락 + `transfer` 상승
> → "옮겨 앉으시는 건 도움이 덜 필요해지셨는데 옷 입기는 도움이 더 필요해지셨습니다. 어떻게 보시나요?"

### (c) 참여 × 비언어 신호

| 조합                       | 읽는 방법                      | 생성할 질문                                                                  |
| -------------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| 참여 정체 + 통증 신호 반복 | 통증이 참여를 막고 있을 가능성 | 일어설 때 찡그리시는 걸 4주 중 3주 봤습니다. 통증일 수 있을까요?             |
| 참여 상승 + 통증 신호 반복 | 무리하고 계실 가능성           | 도움이 덜 필요해지셨는데 일어설 때 아파하시는 것도 봤습니다. 괜찮은 걸까요? |
| 참여 감소 + 신호 없음      | 확인 필요                      | 최근 이런 변화가 있었는데 어떻게 보시나요?                                   |

### (d) 흔들림 자체

`level` 축의 `reversals`가 **2 이상**이면 감지. (갔다, 돌아왔다, 다시 갔다.)
v2는 "3회 이상 반복"이었는데 단위가 불명확했습니다. 방향 전환 횟수로 정의하고 2로 둡니다.

> "세수·양치를 6주 동안 혼자 하셨다 도움이 필요했다를 반복하고 있습니다. 어떻게 보시나요?"

### (e) 자유 기록의 패턴

두 단계로 설계했지만 현재 구현 범위는 1단계까지입니다.

1. **규칙**: 시간대 태그가 같은 자유 기록이 최근 4주 중 3주 이상이면 시간대 패턴으로 감지. LLM 불필요.
2. **후속 범위(미구현)**: 태그가 없거나 부위·상황 패턴을 LLM이 여러 주 자유 기록에서 찾기.

> "오후만 되면 오른쪽 어깨를 자꾸 만지신다"가 4주 중 3주 나오면 시간대 패턴.

**보호자는 이 패턴을 스스로 인식하지 못합니다.** 판정이 아니라 발견이라 안전합니다.

### (f) 도움 수준 동일 + 보조 도구 변화 — v3 추가

`level`이 `no_change`인데 `aid`가 `sustained`이면 감지. 방향 무관.

> "걷기는 지켜보면 되는 건 그대로인데 워커에서 지팡이로 바뀐 지 2주째입니다. 이대로 괜찮을까요?"

### (g) 도움 수준 상승 + 마비 쪽 손 사용 감소 — v3 추가

`level`이 `sustained` 상승인데 `hand`가 `sustained` 하락이면 감지.
치료사가 가장 알고 싶어 하면서 절대 볼 수 없는 장면입니다. 보상 동작으로 잘하게 된 건지 물어야 합니다.

> "식사를 혼자 하시게 됐는데 마비된 손은 더 안 쓰시는 것 같습니다. 괜찮은 걸까요?"

### (h) 도움 수준 동일 + 일관성 하락 — v3 추가

`level`이 `no_change`인데 `consistency`가 `sustained` 하락이면 감지.

> "문턱은 손 잡아드리면 되는 건 그대로인데 요즘은 좋은 날만 그렇습니다. 어떻게 보시나요?"

### 질문 3개 고르기 — 이것도 규칙입니다

감지가 3개보다 많으면 아래 순서로 자릅니다. LLM이 고르지 않습니다.

```
1. 종류 순서:  (a) → (c) 정체+통증 → (g) → (b) → (f) → (h) → (d) → (c) 나머지 → (e)
   종류당 하나씩 순서대로 뽑고, 3개가 안 차면 처음 종류로 돌아가 남은 감지를 이어서 뽑는다
2. 같은 종류 안에 감지가 여럿이면 duration이 긴 것 우선
3. 그래도 같으면 항목 표 순서
```

**위 순서에 적힌 종류는 9개인데 실제 `DetectionType`은 10개입니다.** "(c) 나머지"가 코드에서는
참여 상승+통증(RISE_WITH_PAIN)과 참여 감소+신호 없음(DECLINE_NO_SIGNAL) 둘로 나뉘기 때문입니다.
이 둘은 §7 (c)의 정의상 통증 패턴이 있을 때/없을 때로 나뉘어 같은 케이스에서 동시에 발화할 수 없으므로,
둘 사이의 순서는 실제로는 아무것도 결정하지 않습니다.

§10의 시드에서 (a)는 화장실×걷기, 화장실×계단, 화장실×목욕, 옮겨 앉기×걷기 등 여러 쌍이 나옵니다.
규칙 2로 화장실(duration 4)이 이기고, 규칙 3으로 걷기가 계단·목욕보다 앞섭니다. 그래서 검증된 질문 1이 결정론적으로 나옵니다.

감지가 3개보다 적으면 **빈 칸을 만들지 않습니다.** 1개면 1개. 0개면 준비 카드에 "이번 기간 관찰에서 달라진 것이 없었습니다"와 보호자 직접 입력 칸만 둡니다.
v2는 "정확히 3개"였는데, 없는 질문을 지어내면 §8의 원칙이 깨집니다. **최대 3개**로 바꿉니다.

## 8. LLM 선택과 가드레일

### 이 제품에서 LLM이 하는 일은 좁습니다

**판정은 전부 §6·§7의 규칙 엔진이 끝냅니다. LLM은 언어만 담당합니다.**

LLM은 **주차별 보호자 원문과 규칙 엔진이 찾은 관찰 변화**를 받아, 보호자가 선생님께 여쭤볼
질문을 최대 3개 정리합니다. 질문마다 근거(원문 주차, 관찰 변화)를 함께 내고, 코드 검증기가
근거·숫자·금지 표현을 확인합니다. 판정(무엇이 변했는지)은 여전히 규칙 엔진이 합니다.
원문은 노트북의 Ollama로만 가고 로그에 남지 않습니다.

아래 세 가지는 같은 LLM 경계를 재사용할 수 있는 후속 범위이며 아직 구현되지 않았습니다.

1. 자유 기입 정제 — 한국어 서술 → 구조화 JSON (원문은 보존)
2. 여러 주 기록에서 반복 패턴 추출 (§7 (e) 2단계)
3. 음성 입력 텍스트 정리

**판정은 규칙 엔진에 남고, 코드 검증기가 LLM 질문의 근거와 안전 규칙을 확인합니다.**
LLM은 보호자 원문과 관찰 변화 안에서 질문을 정리하며, 검증을 통과하지 못하면 템플릿으로 돌아갑니다.
이 제한된 합성 범위에 맞춰 소형 모델을 사용합니다.

### 기본: Qwen3 4B, Q8_0 양자화 (Apache 2.0)

- 한국어 포함 29개 이상 언어를 기본 지원하고, **JSON 모드로 구조화 출력**을 제공합니다
- **Apache 2.0** — 별도 계약 없이 상업적 사용 자유. 심사에서 라이선스 질문이 나와도 방어됩니다
- **4B를 고른 이유는 GPU입니다.** 추론 서버가 GTX 1060 6GB라 8B는 4비트로 줄여도 컨텍스트까지 합치면 약 5.9GB로 경계선입니다. 4B Q8_0은 약 4.8GB로 전부 GPU에 올라가고, 8비트라 4비트 8B보다 문장 안정성이 나쁘지 않습니다
- 이 제품에서 LLM이 하는 일이 좁아서(§8 첫 절) 4B로 충분합니다. 프롬프트가 짧으니 컨텍스트는 2K
- Qwen3의 "생각" 모드는 응답 길이·지연과 질문 품질을 함께 바꿀 수 있어 Task 12 실측 뒤 기본값을 정합니다.
  제어 방법은 `reasoning_effort` 설정값이며(`NEXTVISIT_LLM_REASONING_EFFORT`), `/no_think`는 Ollama OpenAI 호환 엔드포인트에서 무시됩니다.

### A/B 해볼 것 (질문 생성 태스크에만)

| 후보              | 양자화 | 이유                                                   |
| ----------------- | ------ | ------------------------------------------------------ |
| Qwen3 4B          | Q8_0   | 기본                                                   |
| Qwen3 8B          | Q4_K_M | 실측해서 GPU에 다 올라가면 유지, 아니면 탈락           |
| Kakao Kanana 1.5 2.1B | Q8_0 | 한국어 특화. Ollama 공식 라이브러리에 없으면 HF GGUF를 Modelfile로 |

방법: 규칙 엔진이 낸 감지 결과 10개를 고정해두고, 각 모델로 질문을 만들어 치료사에게 모델을 가리고 고르게 합니다.
자유 기록 정제와 패턴 추출은 차이가 작으니 이긴 쪽을 그대로 씁니다. Kanana 8B는 Qwen3 8B와 같은 이유로 뺍니다.

### LLM 호출은 전부 비동기 — 화면은 LLM을 기다리지 않습니다

주간 기록을 저장하는 순간 백그라운드에서 질문을 만들어 **캐시**하고, 준비 카드와 치료사용 요약은 캐시를 읽기만 합니다.
노트북 GPU가 느려도 사용자는 모르고, 시드 데이터는 미리 생성해두니 데모에서 대기 시간이 0입니다.
노트북이 꺼져 있으면 가드레일 7번의 템플릿 폴백이 캐시에 들어갑니다. 노트북이 살아나면 다음 저장 때 다시 생성합니다.
같은 케이스의 새로고침은 권위 있는 케이스 행을 먼저 잠가 스냅샷을 읽는 순서로 직렬화합니다. 템플릿 캐시가 커밋된 뒤에만 LLM worker를 `AFTER_COMMIT`으로 보내므로, 늦은 과거 스냅샷 계산이 새 결과를 마지막에 덮을 수 없습니다.

### 배포 환경 — 2026-09-10 결정, 2026-09-17 대체됨

**아래 EC2 계획은 실제로 구축되지 않았고 지금은 폐기된 계획입니다.** 실제 운영은 API·PostgreSQL·

**앱과 DB는 작은 EC2에, LLM은 집 게이밍 노트북에.** GPU 인스턴스는 월 $300이 넘어 쓰지 않습니다. (이력 — 실제로는 미구축)

| 노트북 Ollama              | GTX 1060 6GB, RAM 24GB, Ubuntu Server | 전기세           |

**노트북 단독이 아닌 이유.** 9월 20일~10월 17일 사이 심사위원이 아무 때나 URL을 엽니다.
노트북에 전부 올리면 가정용 회선·전원·터널 중 하나만 죽어도 "배포 안 됨"으로 보입니다.
앱과 DB를 EC2에 두면 노트북이 죽어도 URL은 살아 있고, LLM 호출만 실패하는데 그건 가드레일 7번 템플릿 폴백이 처리합니다.
**노트북이 꺼져도 제품은 규칙대로 동작하고 문장만 조금 덜 자연스러워집니다.**

노트북은 Ubuntu Server에서 NVIDIA 드라이버와 Docker/NVIDIA Container Toolkit을 사용합니다.
Ollama와 cloudflared는 `infra/llm`의 Compose 서비스로 실행합니다. 현재 개인 계정 저장소에는 노트북을 자체 호스팅 runner로 등록하지 않으며 배포도 비활성 상태로 둡니다.
향후 비공개 저장소를 GitHub 조직으로 이전 또는 미러한 뒤에만, 정확한 `main` 배포 workflow로 제한된 `llm-production` 조직 runner group과 `self-hosted`, `linux`, `llm` label을 사용할 수 있습니다.
현재 코드는 CPU·GPU·Tunnel 구성을 갖췄지만 Ubuntu/NVIDIA 실기 검증과 이 외부 runner-group 경계의 운영 설정은 아직 수행하지 않았습니다.
저장소 소유자가 병합 뒤 수행할 작업은 [`infra/llm/OWNER_CHECKLIST.md`](infra/llm/OWNER_CHECKLIST.md), 상세 명령은 [`infra/llm/README.md`](infra/llm/README.md)에 있습니다.
Windows를 남기면 자동 업데이트 재부팅이 심사 기간에 한 번은 터집니다. UptimeRobot 무료 플랜으로 URL과 노트북 둘 다 감시합니다.

### 로컬 실행이 슬라이드가 됩니다

관찰 기록은 개인정보보호법상 **민감정보(건강정보)**입니다.
자체 호스팅하면 규제 문제가 "우리가 풀어야 할 법률 문제"에서 **"우리가 이미 푼 공학 문제"**로 바뀝니다.

> "관찰 기록과 AI 처리는 저희 서버 밖으로 나가지 않습니다."

**문구를 "관찰 기록과 AI 처리"로 한정하는 이유**: 보호자가 폰 키보드의 받아쓰기로 적으시면 그 음성은 구글·애플 서버를 거칩니다.
우리가 만든 기능이 아니라 쓰시던 키보드가 하는 일이지만, "모든 데이터"라고 말하면 그래도 거짓이 됩니다.
저희가 받는 것은 이미 글자가 된 기록이고, 그 뒤로는 서버 밖으로 나가지 않습니다. 문구는 저희가 책임질 수 있는 범위만 말합니다.

호출량이 매우 적습니다(주간 기록 1회, 준비 카드 1회). 4B 양자화면 6GB GPU에서도 충분합니다.

### 반드시 교체 가능하게

Ollama의 OpenAI 호환 엔드포인트에 맞춰 인터페이스를 하나 두세요.
로컬↔호스팅, 모델 교체가 설정 한 줄로 끝나야 합니다.
**모델 선택보다 이 추상화가 더 중요합니다.** GPU 인스턴스가 데모 직전에 죽으면 호스팅 API로 한 줄에 넘어가야 합니다.

### 가드레일 — 모델과 무관하게 코드로 막습니다

프롬프트만 믿지 마세요. **출력 검증을 코드로 넣습니다.**

```
1. 응답은 정확히 하나의 JSON 객체이고 questions/rank/sentence 외 필드가 없어야 함
2. 질문 수와 rank 집합이 입력과 정확히 같아야 함 — 일부만 통과해도 전체 거부
3. 각 문장은 NFC 정규화 뒤 1~200자, 물음표 하나로 끝나고 마크다운·행동 지시가 없어야 함
4. 개선·악화·호전·위험·정상·비정상·회복·좋아지·좋아졌·나빠지·나빠졌·나아지·나아졌·좋아져·나빠져·나아져·좋아짐·나빠짐·나아짐·재활·치료·낙상·점수·처방·운동·진단·기능검사·병원에 가·받으셔야·하셔야를 코드로 거부
5. 입력 템플릿의 모든 아라비아 숫자 토큰을 같은 횟수로 보존해야 함
6. NFC 정규화한 템플릿을 그대로 쓰거나, 마지막 `습니다. `→`는데 ` 또는 `입니다. `→`인데 ` 연결만 같은 앞부분·뒤 질문을 보존한 채 허용; 그 밖의 추가·삭제·동의어·의미 앵커 변경은 전체 거부
7. 최초 호출 + 재생성 2회가 모두 실패하면 전체 LLM 출력을 버리고 템플릿 본문을 유지
```

**7번 폴백이 중요합니다.** 데모 중 모델이 이상한 말을 해도 제품이 규칙을 어기지 않습니다.
§7의 각 감지에 템플릿 문장이 하나씩 있어야 폴백이 성립합니다. §7의 예시 문장이 그 템플릿입니다.
그리고 이 가드레일 구조 자체를 발표자료에 넣으세요. 규제 질문 하나를 통째로 막습니다.
새로고침과 공통 오류 경로의 로그는 원인·케이스·요청값 대신 고정 코드만 남깁니다. 진단 상세를 로그에서 포기하는 대신 보호자 원문·자격증명·생성 문장이 섞여 나갈 경로를 없앴습니다.

## 9. 화면

### 화면 1 — 처음 설정 (1회, 5분)

관계 / 진단명(모름 선택지 필수) / **마비 쪽(왼쪽·오른쪽·없음·모름)** / **말씀으로 불편한 곳을 알려주시는지** / 다음 외래 예약일 / **1주차 기준선**

- 진단명이 관찰 세트를 고릅니다. 마비 쪽이 `hand` 축을, 네 번째 항목이 비언어 관찰을 활성화합니다.
- 외래 예약일은 알림용이 아니라 **준비 카드 생성 시점**이기 때문에 받습니다.
- **1주차 기준선은 온보딩에서 받습니다.** 8항목의 `level`과 적용되는 축을 한 번 다 묻습니다. 화면 2가 "지난주와 달라진 게 있나요"로 시작하기 때문에 비교 대상이 있어야 합니다. v2에는 이 단계가 없어서 첫 주가 성립하지 않았습니다.

### 화면 2 — 주간 관찰 (분기형)

매주 8항목을 다 묻는 구조는 리텐션을 죽입니다. 이렇게 분기합니다.

```
1단계  "지난주와 달라진 게 있나요?"
       └ 없음 → 8항목 전부 carried로 저장, 4단계로 건너뜀

2단계  달라진 항목 선택 (8개 중 다중 선택)

3단계  선택한 항목만: level(그림 선택지) + 그 항목에 적용되는 축 + 자유 기록 한 줄
       선택 안 한 항목은 carried

4단계  비언어 신호 (온보딩에서 활성화된 경우만, 매주 필수)
       — 빈도 정보가 여기서 나오므로 1단계에서 "없음"을 눌러도 반드시 묻는다

5단계  야간 수면 (3단계)
       — 1단계에서 "없음"을 눌러도 반드시 묻는다. 값이 있는 관찰이지 공백이 아니다

6단계  기타 자유 기입 + 시간대 태그
       — 칸을 넓게 두고, 첫 사용 때 폰 키보드의 받아쓰기를 안내한다
```

**4주마다 한 번은 8항목 전체를 다시 묻습니다.**
1단계 질문만으로는 서서히 나빠지는 궤적을 놓칩니다.
매주 조금씩 못하게 되면 매주 "변화 없음"이 눌리고 6주 뒤에 큰 차이가 나 있어도 기록에 안 남습니다.
뇌졸중 회복기에서 흔한 궤적이 정확히 이것입니다.
전체 재확인 시 지난달 답을 함께 보여줍니다. (앵커링 위험이 있으나 놓치는 것보다 낫다고 판단)
전체 재확인 주의 값은 전부 `confirmed`입니다.

### 화면 3 — 경과 (층 2)

두 상태를 반드시 다 구현하세요. **침묵 상태가 기본이고 데모의 핵심 장면입니다.**

- **침묵 상태** — "이번 기간에는 바뀐 항목이 없습니다"
- **변화 확인 상태** — 유지 중인 변화 + 교차 감지 결과 + (해당 주만) sustained→fluctuating 전환 문구

### 화면 3-b — 전체 궤적 탭 (층 2)

기본 화면은 조용하게 두되, 보고 싶은 보호자는 전체를 볼 수 있게 합니다.
`fluctuating`을 포함한 주차별 궤적을 그대로 보여주되, **판정 문구는 붙이지 않습니다.**

### 화면 4 — 진료 준비 카드 (외래 예약일 전날 자동 생성)

- 질문 **최대 3개**. 8개를 들고 가면 의사에게 도움이 아니라 부하입니다. 없으면 없는 대로 둡니다(§7 끝)
- 각 질문에 근거가 되는 관찰이 붙어야 합니다
- 보호자가 편집·추가 가능
- 하단에 치료사가 흘깃 볼 수 있는 요약 3~4줄

### 화면 5 — 치료사용 관찰 요약 (Layer 3)

**목적** — 시간 절약 도구가 아니라, **어르신이 혼자 병원에 갔을 때 부재한 보호자의 대리 진술**입니다.
치료사가 "그건 도움이 된다"고 확인한 유일한 용도입니다.

**날짜에 묶이지 않습니다. 언제든 출력합니다.** 치료는 주 2~3회라 "전날 생성"이 의미가 없고,
어르신이 혼자 가는 날 아침에 보호자가 뽑아주는 게 실제 사용 장면입니다.

**판단 기준: 치료사가 그 자리에서 직접 볼 수 있는 것은 전부 뺍니다. 집에서만 보이는 것만 넣습니다.**

**핵심 — 이전값/현재값이 아니라 주차별 궤적을 보여줍니다.** 축은 항목 아래 부속 행으로 붙습니다.

```
                    1주  2주  3주  4주  5주  6주
화장실 이용          2    2    3    3    3    3
세수·양치            2    2    3    3    2    3
  마비 쪽 손         1    1    1    1    1    1
옮겨 앉기            1    1    1    2    2    2
집 안에서 걷기       2    2    2    2    2    2
  잡는 것           워커  워커  워커  워커  지팡이 지팡이
식사                 2    2    2    3    3    3
  마비 쪽 손         1    1    1    0    0    0
옷 입기              3    3    3    2    2    2
문턱·계단            1    1    1    1    1    1
  일관성            매번  매번  대체로 좋은날 좋은날 좋은날
(목욕 변화 없음)

기립 시 찡그림       ·    ●    ●    ·    ●    ●
기립 시 팔 감쌈      ·    ·    ●    ·    ●    ●

2주차: 달라진 것 없음(복사)     작성자: 딸 (전 주 동일)
```

세수·양치가 3주에 올랐다 5주에 내려갔다 6주에 다시 오른 것이 보여야 합니다.
`2 → 3`으로 요약하면 이 흔들림이 통째로 사라집니다.
식사는 혼자 하시게 됐는데 마비 쪽 손을 안 쓰게 된 것도 같은 표에서 보여야 합니다.

포함

- 주차별 궤적 표 (위 형태). `carried` 주는 옅게, 작성자 변경은 세로선
- 변화 없는 항목은 한 줄로 접기
- 비언어 신호와 빈도 (신호 종류별)
- 보호자 자유 기록 **원문 그대로** (시간대 태그 포함)
- 보호자가 묻고 싶은 것 (최대 3개)
- 기록 밀도 (예: 6주 중 6주 기록, 그중 직접 확인 5주, 작성자 딸)
- 하단 한계 문단

제외

- **우리 쪽 판정 문구 전부** ("1단계 상승" 등) — 치료사마다 견해가 다르므로 **판정은 읽는 사람이 합니다.** 값만
- 교차 해석 — 보호자 카드에만
  - 여기서 "교차 해석"은 궤적 표 위에 얹는 우리 쪽 판정 라벨을 뜻합니다. 보호자가 만든 질문(위 포함 목록의 "보호자가 묻고 싶은 것")은 판정이 아니라, 이 화면이 전달하려는 부재한 보호자의 대리 진술 그 자체이므로 그대로 나갑니다
- 홈프로그램 미수행 사유 — 보호자를 탓하는 것처럼 보임

분량은 A4 한 장이 아니라 **위쪽 3분의 1**입니다. 축이 붙어도 이 분량을 넘기지 마세요. 변화 없는 축은 행을 접습니다. 종이 출력 가능해야 합니다.

### 기술 선택 — 결정됨

9월 20일까지 **배포된 URL**이 있어야 합니다. 앱스토어 심사는 15일 안에 못 끝내므로 **모바일 우선 PWA**로 갑니다.
홈 화면 설치와 전체 화면이 되고, 치료사용 요약의 종이 출력에는 웹이 유리합니다. 링크 하나로 치료사에게 보여드리는 것도 앱보다 웹이 자연스럽습니다.
데모데이 전에 Capacitor로 감싸면 안드로이드 APK가 나오는데, 예선 통과 뒤 일입니다.

**frontend/** — React 19 + Vite + TypeScript, vite-plugin-pwa, Tailwind, react-router, TanStack Query.
계정 없음. 온보딩 때 만든 보호자 토큰을 기기에 저장하고 복구 코드를 보여줍니다. 치료사용 요약은 별도 읽기 전용 링크.
첫 화면(토큰 없을 때)의 "둘러보기" 링크가 아래 시드를 바로 엽니다.

**backend/** — Gradle 멀티모듈, Java 21. **구현된 코드의 안내는 `backend/README.md`에 있습니다.**

- `engine` — 순수 Java. §6 침묵 게이트, §7 교차 감지, 질문 3개 선택. **Spring 의존성 0.** §6 예시 표가 그대로 JUnit 파라미터 테스트
- `api` — Spring Boot 3.5, Spring Data JPA, PostgreSQL. 주차 스냅샷은 JSONB 컬럼 하나. LLM은 `RestClient`로 Ollama의 OpenAI 호환 엔드포인트를 직접 호출. 호출이 한 종류뿐이라 Spring AI를 쓰지 않는다(의존성·버전 궁합 위험 제거). base-url 한 줄로 호스팅 API 전환은 그대로 성립. 상세 계약은 `docs/superpowers/specs/2026-09-05-api-design.md`

**infra/** — 개발용 Postgres Compose와 별도로 `infra/llm`에 Ollama 0.33.3 CPU/GPU, 모델 초기화, Cloudflare Tunnel, smoke, GitHub Actions 배포 구성이 있습니다. 현재 개인 계정 저장소에서는 노트북 runner를 등록하지 않고 `LLM_DEPLOY_ENABLED`를 absent/false로 둡니다. 조직 runner group의 외부 제한을 갖춘 뒤에만 배포를 검토합니다.

**로컬 실행**

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # 이 맥은 기본 java가 26
cd backend
docker compose up -d                                # Postgres 16
./gradlew :api:bootRun                              # http://localhost:8080
curl -s -X POST localhost:8080/demo | jq            # 시드 케이스 + 보호자 토큰 + 치료사 링크
curl -s localhost:8080/me/prep-card -H "X-Guardian-Token: <guardianToken>" | jq
```

LLM은 기본 비활성이므로 API 개발에 Ollama가 필요하지 않습니다. 로컬 CPU 컨테이너와 실제 OpenAI 호환 smoke는 `infra/llm/README.md`를 따릅니다.

테스트는 도커 없이 돈다(H2). `./gradlew test`.
