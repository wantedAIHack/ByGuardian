# 보호자 기록 기반 질문 정리 설계

작성일: 2026-09-17 · 상태: 승인됨(제품 소유자, 대화로 섹션별 승인) · 브랜치: `ops/single-host-completion`

이 문서는 LLM이 이 제품에서 맡는 일을 다시 정한다. 아래 문서의 해당 부분을 대체한다.

- `README.md` §1 "검증된 것", §8 "이 제품에서 LLM이 하는 일은 좁습니다"
- `docs/superpowers/specs/2026-09-05-api-design.md`의 질문 캐시·LLM 다듬기 부분
- `docs/superpowers/specs/2026-09-07-llm-server-design.md`의 "templateSentence만 전달" 경계

## 0. 왜 다시 설계하나

### 치료사가 좋다고 한 것

README §1은 치료사 인터뷰에서 두 예시 **문장**이 "너무 좋다"는 평가를 받았고, 그 문장들이 산출물의 기준이라고 적었다. 제품 소유자가 2026-09-17에 이 해석을 바로잡았다.

치료사가 좋다고 한 것은 문장이 아니라 **구조**다. 보호자가 기록할 때마다 자기 생각을 남기고, 치료사에게 보여줄 때 LLM이 그 생각들을 모아 "치료사에게 무엇을 어떻게 물으면 좋을지" 정리해 주는 구조다.

### 지금 구현이 막고 있는 것

기존 구현은 잘못된 해석을 그대로 따랐다.

| 장애물 | 위치 | 결과 |
| --- | --- | --- |
| 보호자 원문을 LLM에 보내지 않음 | README §8, `QuestionRewritePrompt` | 핵심 재료가 빠짐 |
| 템플릿과 같거나 마지막 "습니다. "를 "는데 "로 잇기만 허용 | `QuestionOutputGuard.isPermittedSurfaceRewrite` | LLM이 할 수 있는 일이 문자열 치환 하나 |
| 질문 슬롯이 규칙 엔진 감지에 고정 | `QuestionService.refresh`, `RANK_SET` 규칙 | 보호자 걱정에서 질문이 나올 수 없음 |
| 생각 모드가 꺼지지 않음 | `/no_think`를 Ollama OpenAI 호환 엔드포인트가 무시 | 시도당 40~90초, 본문이 빈 채 끝나는 실패 |

2026-09-17 운영 실측에서 수정 전 생성 4건 중 1건만 채택됐다(`docs/qa/2026-09-17-llm-activation.md` 8~9절). 같은 날 추가된 "연결 강제"와 예시 한 쌍(`d38ccc8`)은 채택률을 올렸지만, 이미 "-는데"가 있는 10개 중 6개 질문 유형을 더 읽기 어렵게 만들었다. 이 설계가 그 부분을 대체한다. `reasoning_effort` 전달은 설정값으로 남긴다(3.4절).

## 1. 결정 요약

- LLM은 **주차별 보호자 원문 + 규칙 엔진이 찾은 관찰 변화**를 받아, 보호자가 치료사에게 물을 **질문을 최대 3개** 정리한다.
- 질문마다 **근거**(원문 주차, 관찰 변화 번호)를 함께 낸다. 코드 검증기가 근거와 숫자를 확인한다.
- 평소에는 LLM 질문이 보인다. LLM이 꺼져 있거나, 보호자 원문이 하나도 없거나, 실패하면 지금의 **템플릿 질문**이 보인다.
- 보호자는 진료 준비 카드에서 질문을 **고치고, 지우고, 추가**한다. 저장하면 **확정 목록**이 된다.
- 확정 목록이 있으면 새 기록이 와도 보이는 목록은 바뀌지 않는다. 새 정리안은 제안으로 보관하고 "다시 정리하기"로 교체한다.
- 기존 "추가 질문" 칸은 확정 목록에 합친다.
- 치료사 화면에는 확정 목록(없으면 현재 목록)이 **근거 주차의 원문**과 함께 나온다.
- 정리 중에는 화면을 막지 않고 **안내 문구**만 보인다.
- 생각 모드는 **설정값**이다. 기본값은 6.2절의 품질 비교로 정한다.
- 판단 금지 경계는 그대로다. 진단, 원인 단정, 점수, 운동·치료 권유, 호전/악화 판단을 하지 않는다.

## 2. 흐름

```
PUT /me/weeks/{w}
  └ QuestionService.refresh(case)
      ├ 규칙 엔진 실행 → 템플릿 질문 캐시 저장 (화면은 여기서 바로 응답)
      └ LLM 켜짐 + 원문 있음 → 상태 LLM_PENDING, AFTER_COMMIT 이벤트
            └ 단일 작업 스레드
                ├ SynthesisInputAssembler: 변화 목록 + 주차별 원문 조립
                ├ LlmClient.complete(prompt)
                ├ SynthesisValidator: 형식·근거·숫자·금지 표현 검사
                └ 통과 → 캐시를 LLM 질문으로 교체 / 실패 → 템플릿 유지
```

- 트랜잭션과 잠금 순서는 기존과 같다(case → snapshots → cache). 늦게 끝난 오래된 생성은 `generationId`가 달라 결과를 쓰지 못한다.
- 확정 목록이 있는 케이스도 정리는 돈다. 결과는 캐시(제안)에만 쓰고 확정 목록은 건드리지 않는다.

## 3. LLM 계약

### 3.1 입력 조립 (`SynthesisInputAssembler`)

- 관찰 변화: 엔진이 고른 감지마다 `D1`, `D2`… 번호, 템플릿 문장, 관련 항목 코드.
- 보호자 원문: 스냅샷마다 자유 기록(`freeNote.text`)과 항목별 메모(`ItemValues.note`)를 주차·시간대와 함께 넣는다.

  ```
  W3 · 오후 · 자유 기록: "…"
  W3 · 화장실 이용 메모: "…"
  ```

- 원문 전체에 글자 수 상한을 둔다(`nextvisit.llm.synthesis-max-note-chars`, 기본 4000). 넘으면 **최근 주부터** 넣고 오래된 주를 뺀다. 뺀 주는 근거로 댈 수 없다.
- 원문이 하나도 없으면 LLM을 부르지 않고 템플릿 목록을 쓴다.
- 조립은 순수 함수로 분리한다. 나중에 원문 구조화 단계(접근법 B)를 이 앞에 끼울 수 있게 하기 위해서다.

### 3.2 지시 (`QuestionSynthesisPrompt`)

- 역할: 뇌졸중 후 집에서 지내는 환자의 보호자를 돕는다. 다음 진료에서 보호자가 치료사에게 **직접 물을 질문**을 정리한다.
- 말투: 보호자가 말하는 존댓말 질문. "~까요?", "~나요?", "~가요?" 중 하나로 끝낸다(검증기의 의문형 어미 규칙과 맞춘다).
- 호칭: 치료사를 부를 때는 "선생님"이라고 쓴다. 금지어 목록에 "치료"가 있어 "치료사"라는 단어가 거부되기 때문이다(10절 열린 결정 1).
- 사실: 입력의 원문과 관찰 변화에 있는 것만 쓴다. 입력에 없는 숫자, 기간, 증상을 만들지 않는다.
- 금지: 진단, 원인 단정, 점수, 운동·치료·약 권유, 좋아졌다/나빠졌다는 판단, 지시형 문장.
- 개수: 1~3개. 서로 겹치지 않게 한다.
- 출력: JSON만.

  ```json
  {"questions":[{"sentence":"…?","detections":["D1"],"noteWeeks":[3,5]}]}
  ```

### 3.3 검증 (`SynthesisValidator`)

하나라도 어기면 그 시도는 실패다. 규칙마다 실패 코드를 로그에 남기고, 문장과 원문은 남기지 않는다.

| 코드 | 규칙 |
| --- | --- |
| `JSON_OBJECT`, `ROOT_FIELDS`, `QUESTIONS_ARRAY`, `QUESTION_FIELDS` | 위 JSON 형태와 정확히 일치 |
| `QUESTION_COUNT` | 1~3개 |
| `SENTENCE_LENGTH` | 문장 10~160자 |
| `QUESTION_MARK` | 기존 의문형 어미 패턴(`나요|까요|가요|습니까|지요|죠`)으로 끝남 |
| `MARKDOWN` | 기존 패턴 그대로 |
| `DIRECTIVE` | 기존 패턴에서 `해야`만 뺀다. "어떻게 해야 할까요?"는 보호자의 자연스러운 질문이고, "하셔야"는 금지어 목록이 이미 막는다 |
| `FORBIDDEN_WORD` | `Templates.containsForbiddenWord` 그대로 |
| `DUPLICATE` | NFC 정규화 후 같은 문장 없음 |
| `BASIS_EMPTY` | `detections`와 `noteWeeks` 중 적어도 하나가 비어 있지 않음 |
| `UNKNOWN_DETECTION` | 모든 `detections`가 입력에 있는 번호 |
| `UNKNOWN_NOTE_WEEK` | 모든 `noteWeeks`가 입력에 실제로 들어간 원문 주차 |
| `UNSUPPORTED_NUMBER` | 문장 속 모든 숫자가 근거로 댄 변화 문장, 근거로 댄 원문, 또는 근거 주차 번호 안에 있음 |

`SURFACE_REWRITE`와 `RANK_SET`은 없앤다. 기존 `QuestionOutputGuard`와 `QuestionRewritePrompt`는 새 검증기와 지시로 교체한다. 템플릿 경로(3.5절)는 검증기를 거치지 않는다.

### 3.4 모델 설정

- 모델: `qwen3:4b-q4_K_M` 유지(GTX 1060 6GB에 전부 올라감).
- 생각 모드: `nextvisit.llm.reasoning-effort` 설정값. `none`이면 요청에 `reasoning_effort:"none"`을 넣고, 비어 있으면 필드를 보내지 않는다. 기본값은 6.2절 결과로 정한다.
- 출력 한도와 읽기 제한은 6.2절 측정으로 다시 정한다. 생각 모드를 켜면 사고 토큰까지 담을 만큼 한도를 올린다.
- 재시도: 기존과 같이 최대 3회.
- 작업 스레드는 하나다. 생각 모드에서 동시에 여러 보호자가 저장하면 뒤 요청이 기다린다. 대회 규모에서는 받아들이고 한계로 기록한다.

### 3.5 템플릿 경로

LLM이 꺼져 있거나, 원문이 없거나, 3회 모두 실패하면 규칙 엔진 템플릿 질문을 그대로 쓴다. 템플릿 문장은 캐시에 항상 먼저 저장되므로 화면이 비는 일은 없다.

## 4. 저장 구조와 API

### 4.1 저장

- `question_cache.body`의 질문 항목에 `origin`(`TEMPLATE | LLM | CAREGIVER`)과 `basis`(`detections`, `noteWeeks`)를 추가한다. 기존 `templateSentence`, `sentence`, `source`는 그대로 둔다(기존 화면 호환).
- `question_cache.status`는 기존 값(`READY`, `LLM_PENDING`, `LLM_DONE`, `LLM_FAILED`)을 그대로 쓴다. 새 값을 만들지 않는다.
- `cases`에 `confirmed_questions`(JSON, null 허용)와 `confirmed_at`(시각, null 허용)을 추가한다. 마이그레이션 `V3__confirmed_questions.sql`을 `db/migration/postgresql`과 `db/migration/h2` 두 곳에 각 DB 문법으로 둔다.
- 기존 `extra_questions`는 일괄 변환하지 않는다. 화면에서는 목록 뒤에 `CAREGIVER` 질문으로 합쳐 보여주고, 보호자가 처음 목록을 저장할 때 확정 목록으로 옮긴 뒤 비운다.

### 4.2 보이는 목록 결정

1. `confirmed_questions`가 있으면 그것.
2. 없으면 캐시의 현재 질문 + 기존 추가 질문.

`suggestionAvailable`은 확정 목록이 있고, 캐시의 `generated_at`이 `confirmed_at`보다 늦으며, 캐시 상태가 `LLM_PENDING`이 아닐 때 참이다.

`generationStatus`는 캐시 상태에서 이렇게 정한다.

| 캐시 상태 | `generationStatus` |
| --- | --- |
| `LLM_PENDING` | `PENDING` |
| `LLM_DONE` | `DONE` |
| `LLM_FAILED` | `FAILED` |
| `READY` (LLM 꺼짐 또는 원문 없음) | `TEMPLATE_ONLY` |

### 4.3 API (기존 필드는 지우지 않는다)

- `GET /me/prep-card` 추가 필드
  - `items[]`: `id`, `sentence`, `origin`, `basis.detections[]`(변화 라벨과 기존 근거 형식), `basis.notes[]`(`week`, `timeTag`, `text`)
  - `generationStatus`: `PENDING | DONE | FAILED | TEMPLATE_ONLY`
  - `edited`: 확정 목록 존재 여부
  - `suggestionAvailable`
- `PUT /me/prep-card/questions`: 본문 `{"items":[{"id":"q1","sentence":"…?"},{"id":null,"sentence":"…?"}]}`. 최대 8개, 문장당 200자, 빈 문장 불가.
  - `id`가 지금 보이는 목록의 항목과 맞으면 그 항목의 `origin`과 `basis`를 서버가 이어받는다. 문장이 달라졌으면 항목에 `edited: true`를 기록한다.
  - `id`가 없거나 맞지 않으면 `origin: CAREGIVER`, 근거 없음으로 저장한다.
  - 클라이언트가 보낸 근거는 믿지 않는다.
- `POST /me/prep-card/regenerate`: 확정 목록을 지워 현재 캐시를 보이게 한다. 확정 목록의 `CAREGIVER` 질문은 버리지 않고 추가 질문 칸으로 되돌려 새 목록 뒤에 다시 붙인다. 보호자가 고친 LLM·템플릿 질문은 새 정리안으로 바뀐다. 캐시가 확정 시각보다 새롭지 않으면 새 정리를 시작한다.
- 기존 `PUT /me/prep-card/extra`는 남긴다. 확정 목록이 있으면 추가 질문을 확정 목록 끝에 반영한다.
- 치료사 요약: 기존 화면이 `questions`와 `extraQuestions`를 이어 붙여 보여주므로 겹치지 않게 나눈다. `questions`는 보이는 목록 중 `CAREGIVER`가 아닌 문장, `extraQuestions`는 `CAREGIVER` 문장이다. 새 `questionDetails[]`(`sentence`, `origin`, `noteWeeks`)는 보이는 목록 전체를 순서대로 담는다.

### 4.4 배포 순서

프런트는 `main` 병합 시 Cloudflare Pages가 자동 배포하고, 백엔드는 jar를 수동으로 올린다. 그래서 API는 추가만 하고, 배포는 **백엔드 먼저 → 운영 확인 → 프런트 병합** 순서다. 새 프런트는 새 필드가 없으면 기존 필드로 화면을 그린다.

## 5. 화면

### 5.1 진료 준비 카드 (보호자)

- 목록 하나: "진료실에서 여쭤볼 것".
- 질문마다 접었다 펴는 근거: "3주·5주 기록, 화장실 이용 변화". 원문 발췌와 기존 관찰 근거 표를 재사용한다.
- 편집 모드: 문장 고치기(여러 줄 입력칸), 지우기, 추가하기, 저장. 저장 중 편집 보존 규칙은 기존 추가 질문 편집과 같다.
- 상태 안내(`aria-live="polite"`, 색으로 상태를 표현하지 않음)
  - `PENDING`: "기록을 바탕으로 질문을 정리하고 있어요." 템플릿 질문은 그대로 보인다.
  - 완료 시 편집 중이 아니면 그 자리에서 교체한다. 편집 중이면 "정리안이 준비됐어요 · 보기"만 보인다.
  - `suggestionAvailable`: "새 기록이 반영된 정리안이 있어요 · 다시 정리하기".
  - `FAILED`, `TEMPLATE_ONLY`: "관찰 기록에서 나온 질문을 보여드려요."
- `PENDING` 동안 5초마다 다시 조회한다. 5분이 지나거나 화면을 떠나면 멈춘다.

### 5.2 치료사 화면

- 질문 옆에 "보호자 기록 3주·5주". 누르면 원문 목록의 해당 주로 이동한다.
- 인쇄에서도 근거 주차가 글자로 남는다.

두 화면 모두 2026-09-15 따뜻한 관찰 노트 디자인(본문 18px, 주요 버튼 56px, 색으로 상태를 표현하지 않음)을 따른다.

## 6. 검증

### 6.1 백엔드 (테스트 먼저)

- 입력 조립: 원문·항목 메모·시간대가 주차와 함께 들어감, 상한에서 최근 주가 남음, 원문이 없으면 호출하지 않음.
- 검증기: 3.3절 규칙마다 실패하는 테스트를 먼저 쓴다. 특히 지어낸 숫자, 없는 주차, 근거 없는 질문, 금지 표현.
- 상태 전이: 미수정 목록 자동 교체, 확정 목록 유지와 `suggestionAvailable`, 다시 정리하기, 추가 질문 지연 이관, 오래된 `generationId` 결과 무시.
- 호환: 기존 프런트가 쓰는 `questions[].sentence/source/evidence`, `extraQuestions`가 그대로 있음.

### 6.2 품질 평가 (생각 모드 기본값)

- 원문이 있는 합성 케이스 3개 × 6주를 저장소에 fixture로 둔다. 실제 보호자 문장을 쓰지 않는다.
- 노트북 Ollama에 읽기 전용 HTTP 호출로 생각 끔/켬을 각각 케이스당 3회 돌린다.
- 비교: 검증 통과 수, 시도별 소요 시간, 출력 토큰 수. 그리고 **케이스별 질문 세트를 제품 소유자에게 보여주고 판단받는다.** 숫자만으로 좋은 질문을 판정하지 않는다.
- 결과로 `reasoning-effort`, 출력 한도, 읽기 제한 기본값을 정하고 `docs/qa/`에 기록한다.

### 6.3 프런트

- 목록 편집, 상태 안내, 재조회 중단, 편집 중 교체 방지 단위 테스트.
- 브라우저 테스트: CI는 LLM이 꺼져 있으므로 템플릿 경로를 검증하고, LLM 경로는 합성 응답으로 검증한다.

### 6.4 운영

합성 데모 케이스로: 기록 저장 → 정리 중 안내 → 정리 완료 → 편집·확정 → 새 기록 → 새 정리안 안내 → 다시 정리하기 → 치료사 화면 근거 이동.

## 7. 문서와 인수인계

- README §1의 인터뷰 해석과 §8의 LLM 역할을 이 문서대로 고친다.
- 대체되는 기존 설계서 부분에 이 문서 링크를 단다.
- 구현 계획서 맨 위에 "현재 위치 / 다음 할 일 / 열린 결정"을 두고, 작업마다 체크박스와 함께 같은 커밋에서 갱신한다. 다른 도구가 저장소만 보고 이어받을 수 있어야 한다.

## 8. 이번 범위 밖

- 원문을 먼저 구조화하는 2단계(접근법 B)
- 작업 스레드 여러 개, 대기 순번 표시
- 외부 LLM
- 운영 DB에 남은 합성 데모 데이터 정리
- 보호자 원문 자체의 편집·삭제 기능 변경

## 9. 한계

- 보호자 원문이 짧거나 없으면 질문은 템플릿에 가깝다.
- 숫자 검사는 지어낸 숫자를 막지만, 숫자 없는 과장("매번", "항상")은 막지 못한다. 보호자 편집과 치료사 화면의 원문 근거가 그 보완이다.
- 단일 작업 스레드라 동시 저장이 몰리면 정리가 늦어진다.
- 실제 보호자·치료사 대상 사용성 검증은 하지 않았다.

## 10. 열린 결정

1. **금지어 목록과 보호자 원문.** 엔진의 금지어(`Templates.FORBIDDEN`)에는 "치료", "재활", "운동", "낙상"이 들어 있다. 제품이 스스로 권하거나 판단하는 문장을 막으려고 만든 목록이지만, 보호자가 원문에 "운동할 때", "치료 시간에"라고 적은 걱정에서 나온 질문도 함께 막힌다. 기본값은 **목록을 그대로 적용**하고, 지시문에서 "선생님" 호칭과 해당 단어 회피를 요구한다. 근거로 댄 원문에 그 단어가 실제로 있을 때만 "치료·재활·운동·낙상"을 허용할지는 제품 소유자가 정한다. "개선·악화·호전·정상·진단·점수·처방" 같은 판단 어휘는 어떤 경우에도 허용하지 않는다.
2. **생각 모드 기본값, 출력 한도, 읽기 제한.** 6.2절 품질 비교 뒤에 정한다.
