# API 후속 작업 — 프론트엔드 계획을 쓰기 전에 읽으세요

`backend/api`(api-core)는 2026-09-06에 main으로 병합됐습니다. 커밋 20개, 엔진 112 + API 59 테스트 전부 통과.
이 문서는 전체 리뷰에서 나왔지만 이번 범위 밖으로 넘긴 것들입니다. **프론트엔드 계획의 첫 태스크가 1·2번을 반영해야 합니다.**

엔진 쪽 후속은 `2026-09-05-engine-followups.md`에 따로 있습니다. 특히 **금지 어휘 목록은 LLM 모듈이 병합되기 전에 넓혀야 합니다.**

---

## 1. 프론트엔드가 바로 막히는 것

**없습니다.** CORS와 오류 형태는 병합 전에 고쳤습니다. 아래는 화면을 만들다 부딪힐 것들입니다.

### 화면 3(경과)에 정렬 힌트가 없습니다

`GET /me/progress`의 `changes`에는 상한도 우선순위도 없습니다. 데모 케이스에서 변화 문장 7개에 질문 3개가 함께 나옵니다.
§6의 층별 처리 표가 그렇게 시키는 게 맞지만, "조용한 화면"이 일곱 줄일 때 어떻게 보일지는 화면 설계가 정해야 합니다.
API는 항목 표 순서 말고는 아무 힌트도 주지 않습니다. 필요하면 `changes`에 정렬 키를 추가하세요.

### 치료사 링크 URL의 주인이 모호합니다

`POST /me/therapist-link`는 `/t/{token}`이라는 상대 경로를 돌려줍니다. 그 경로는 API가 JSON으로 서빙하는 주소이기도 하고, 프론트가 사람이 읽을 페이지로 만들 주소이기도 합니다.
프론트는 `token`만 받아 자기 오리진으로 링크를 조립하면 됩니다. 인쇄·QR용 절대 URL이 필요하면 API에 기준 URL 설정을 추가하세요.

### `PUT /me/prep-card/extra`만 배열을 돌려줍니다

API 전체에서 유일하게 객체가 아닌 응답입니다. 클라이언트 코드가 일관되길 원하면 감싸세요.

## 2. 프론트엔드 모듈과 함께 고칠 것

| 항목 | 내용 |
| --- | --- |
| 빈 주 건너뛰기 테스트 | 컨트롤러 단에서 한 주를 건너뛴 뒤 "달라진 것 없음"을 눌렀을 때 가장 최근 기록을 복사하는지 검증하는 테스트가 없습니다. 저장소 질의는 이미 고정돼 있습니다. |
| 중복 제출 409 | `DataIntegrityViolationException` → 409는 넣었지만, 같은 케이스·주차 동시 PUT 경로는 테스트가 없습니다. PWA는 모바일에서 이중 제출이 납니다. |
| 4줄 요약의 다축 결합 | 여러 축이 한 줄에 쉼표로 이어지는 분기가 데모에서 이제 실제로 돕니다. 테스트로 고정하세요. |
| 준비 카드의 중복 파싱 | `PrepCardService`가 질문마다 항목·축별로 스냅샷을 다시 파싱합니다. `TrajectoryMapper.items`는 고쳤지만 이 경로는 남아 있습니다. |
| 데모·헬스 분기 테스트 | 데모 차단 스위치가 꺼졌을 때와 헬스체크가 503을 내는 분기에 테스트가 없습니다. |

## 3. 배포 모듈에서 할 것

1. **로깅.** 예외 처리기 외에는 로그가 없습니다. 심사위원이 "안 되던데요"라고 하면 읽을 게 없습니다. 요청 로그 하나, 예외 로그 하나면 충분합니다.
2. **데모 엔드포인트 속도 제한.** 인증 없는 쓰기이고 호출마다 열 행쯤 씁니다. 한 달간 무인으로 열어두는 URL이라 스캐너 한 대면 부담이 됩니다. 차단 스위치(`NEXTVISIT_DEMO_ENABLED`)는 있으니 켠 채로 제한만 붙이면 됩니다.
3. **Dockerfile과 `infra/`.** `backend/docker-compose.yml`은 개발용 Postgres만 있습니다. api 서비스도 Caddy도 없습니다.
4. **CORS 오리진.** `NEXTVISIT_CORS_ORIGINS`로 주입합니다. 기본값은 `http://localhost:5173`이라 배포 시 반드시 바꿔야 합니다.
5. **헬스체크는 이제 DB를 건드립니다.** UptimeRobot이 상수를 보는 게 아니라 실제 상태를 봅니다.

## 4. 그냥 두기로 한 것

전체 리뷰가 지적했지만 고치지 않기로 한 것들과 이유입니다.

- **엔티티가 생성자에서 UUID를 정해서 insert마다 select가 한 번 더 붙습니다.** 쓰기가 케이스당 주 1회입니다.
- **주간 저장의 "기준선이 없습니다" 분기가 `BASELINE_ONLY` 코드를 재사용합니다.** 온보딩이 같은 트랜잭션에서 1주차를 쓰므로 도달 불가입니다. 손댈 일이 있으면 500으로 바꿔서 미래의 버그가 조용히 클라이언트 잘못으로 보이지 않게 하세요.
- **추가 질문의 길이 검사가 trim 전에 돕니다.** 200자 경계에서 공백 몇 개 차이입니다. 과하게 거부하는 방향이라 안전합니다.
- **치료사 링크 동시 재발급이 활성 링크 둘을 남길 수 있습니다.** 최악이 옛 QR이 계속 도는 것입니다.
- **인증 필터 안에서 예기치 못한 예외가 나면 JSON 오류 본문을 못 씁니다.** 여전히 닫히는 쪽으로 실패합니다.
- **카탈로그 응답을 요청마다 다시 만듭니다.** 항목이 여덟 개입니다.

## 5. 구조적으로 알아둘 것

### 인증 컨텍스트의 케이스 엔티티는 분리된 상태입니다

필터가 트랜잭션 밖에서 읽고 `open-in-view: false`이므로, `ctx.kase()`를 통해 쓰면 조용히 아무 일도 안 일어납니다.
`CaseService.updateCase`와 `PrepCardService.saveExtra`가 id로 다시 읽는 이유가 이것입니다. **쓰기 전에는 반드시 다시 읽으세요.**
반대로 `PrepCardService.card`는 분리된 인스턴스에서 추가 질문을 읽으므로, 다른 보호자가 방금 고쳤다면 그 요청에서는 옛 목록이 보입니다.

### 관찰 세트 변경은 편집이 아니라 마이그레이션입니다

엔진의 입력 생성자가 세트에 없는 항목 코드를 거부합니다. README §11이 항목 조정을 예고하고 있는데, 항목을 하나 빼는 날 기존 케이스가 전부 읽기에서 터집니다.
엔진 후속 문서에도 같은 내용이 있습니다.

### 층 계약이 어디까지 구조로 강제되는지

- **층 1** — 구조. 단 두 가지 완화가 있습니다. 같은 주 덮어쓰기는 이전 본문을 남기지 않고(설계 3절이 승인), 비언어 관찰이 꺼진 케이스에 보낸 `painSignal`은 조용히 버려집니다.
- **층 2** — 보여주는 것은 구조, 숨기는 것은 관례. `changes`는 흔들림을 흘릴 수 없지만 `questions`는 캐시에서 그대로 옵니다. 흔들림 질문이 보호자 화면에 나올 수 있다는 건 README §6에 명시했습니다.
- **층 3** — 판정 필드는 구조로 불가능(궤적 매퍼가 판정 타입을 import하지 않습니다), 판정 개념은 산문으로 들어옵니다. 생성된 질문이 기간과 방향을 담고 있습니다. README §9 화면 5에 그게 의도라고 적었습니다.
